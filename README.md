# AutoForecast Lab

> **An end-to-end machine learning forecasting platform**

AutoForecast Lab turns a raw time series into validated data, engineered features, a model selected against naive baselines, holdout metrics, and a multi-step forecast beyond the last observation. You can use it through a FastAPI service or an interactive Streamlit dashboard.

The project shows how a forecasting model can be developed, evaluated honestly and served with modern software engineering practices: automated tests, static type checking, continuous integration and containerization.

---

## What it does

- Upload a CSV time series (or send JSON to the API)
- Validate it: unparseable or duplicate timestamps, missing or non-numeric targets, too few rows
- Sort the series and build lag, rolling and calendar features without look-ahead
- Compare four models with **walk-forward validation**, including **naive and seasonal-naive baselines**
- Report every model on an untouched **holdout** period
- Refit the selected model and **forecast N periods into the future**
- Download holdout predictions and future forecasts

---

## Results on the sample data

`data/sample_sales.csv` is one year of synthetic daily sales with a trend, yearly and weekly seasonality, and autocorrelated noise. It is generated by `scripts/generate_sample_data.py` with a fixed seed.

| Model | Walk-forward RMSE | Holdout RMSE (last 30 days) |
|---|---|---|
| Naive (yesterday's value) | 11.14 | 10.09 |
| Seasonal naive (same day last week) | 5.74 | 7.25 |
| Random forest on levels | 5.73 | 6.10 |
| **Random forest on changes (selected)** | **4.25** | **4.66** |

The selected model cuts holdout error by **36% versus seasonal naive** and **54% versus naive**.

**Why predict changes?** Tree models can only predict values they saw during training, so a forest trained on *levels* cannot follow a rising trend past the training range. Its forecasts plateau. Predicting the *change from the last value* and adding it back removes that limit.

## Methodology

### Features (no look-ahead)

- **Lags:** 1 and 7 periods
- **Rolling mean and standard deviation:** 7 and 14 periods, computed on the series shifted by one period, so a row's features never include its own value
- **Calendar:** year, month, quarter, day of week, day of month, week of year

### Model selection

1. The last 30 rows are held out and never used for selection.
2. Within the remaining rows, an **expanding-window (walk-forward)** backtest refits each model on all data up to each fold and forecasts the next block.
3. The model with the lowest pooled walk-forward RMSE is selected.
4. Every model is then scored on the holdout, so the selected model is compared with the baselines on unseen data.

### Multi-step forecasting

Future lag and rolling features are unknown, so the forecast is **recursive**. Each prediction is appended to the history and the next step's features are rebuilt from it. Errors can compound as the horizon grows.

### Candidate models

| Name | Description |
|---|---|
| `naive` | Last observed value |
| `seasonal_naive` | Value from one season (7 periods) earlier |
| `random_forest` | Random forest predicting levels |
| `random_forest_differenced` | Random forest predicting the change from the last value |

Any object with `name`, `fit(X, y)` and `predict(X)` can be added through the `Forecaster` protocol.

## Architecture

```text
Raw time series (CSV / JSON)
        │
        ▼
Validation ──► fails fast with a list of issues
        │
        ▼
Sort + type conversion
        │
        ▼
Feature engineering (lags, rolling stats, calendar)
        │
        ▼
Chronological holdout split
        │
        ▼
Walk-forward backtest of all models ──► select lowest RMSE
        │
        ▼
Holdout evaluation of all models
        │
        ▼
Refit selected model ──► recursive multi-step forecast
        │
        ▼
FastAPI service / Streamlit dashboard
```

## Quick start

```bash
git clone https://github.com/weijiap/forecasting-platform.git
cd forecasting-platform
uv sync
```

Run the dashboard, then upload `data/sample_sales.csv`:

```bash
uv run streamlit run dashboard/app.py
```

Run the API (interactive docs at `http://127.0.0.1:8000/docs`):

```bash
uv run fastapi dev src/forecasting_platform/api/main.py
```

Run all checks:

```bash
uv run python -m ruff format --check .
uv run python -m ruff check .
uv run python -m mypy src scripts tests
uv run python -m pytest
```

## API

| Method | Endpoint | Description |
|---|---|---|
| GET | `/health` | Service status |
| POST | `/forecast/summary` | JSON `timestamps`, `values` and `horizon` → selected model, holdout metrics, model comparison, future forecast |
| POST | `/forecast/upload` | CSV upload (`horizon` query parameter) → the same, plus holdout predictions |

Invalid data returns **400** with the validation issues; malformed requests return **422**.

## Docker

```bash
docker build -t forecasting-platform .
docker run --rm -p 8000:8000 forecasting-platform
```

The container serves the API on port 8000 as a non-root user. CI builds the image after the quality checks pass.

## Limitations and roadmap

- **Point forecasts only.** Next step: prediction intervals from walk-forward residuals or quantile models.
- **One series at a time.** Next step: a global model across many related series.
- **Fixed feature set.** Season length is 7, which suits daily data. Next step: choose lags and season length from the detected frequency.
- **More models:** gradient boosting and classical baselines (ETS / ARIMA) in the same comparison.
- **Deployment:** the container is deployment-ready but not hosted. Next step: a cloud deployment with monitoring of forecast error over time.
